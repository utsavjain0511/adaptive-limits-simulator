# Design rationale — Adaptive Limits Lab

> Skeleton pre-filled with the decisions made during the build. Edit freely; the "Time spent" line is yours to fill in.

## Why this theme and approach
- Themes 1 + 3: overload behaviour is *emergent* — a queue that looks fine at 90% load falls off a cliff at 110% — and that is badly served by static explanation. A live A/B simulation lets a reader see the cliff, then see each mitigation move it.
- Scoped to one backend and one variable (the admission-control policy) so every lesson isolates exactly one idea and the four lessons build on each other: shed → limit the right resource → static limits can't track capacity → measure capacity instead.

## What makes it interesting / non-obvious
- **Same arrivals, same seed, two policies.** Both runs draw arrivals from the same seeded RNG and per-request jitter is derived from the request id, so any difference between the red and teal lines is causal, not noise.
- **The failure mode is the real one.** The backend is a FIFO worker pool with variable service times plus a client deadline: work completed after the client gave up counts as failure. So a backend running flat out at full capacity still shows 0% goodput once the queue wait passes the deadline — the production symptom of "100% busy, nobody served" — without inventing any extra physics.
- **Lesson 2 is a Little's-law argument made visible.** Both limiters are tuned to the same 200 rps; only latency changes. The RPS limiter can't see the resource it is supposed to protect.
- **Lesson 3 → 4 argues *why* adaptive limiters exist** (capacity is not a constant) before showing them. AIMD and Gradient are the real algorithm families behind Netflix `concurrency-limits`, gRPC and Envoy adaptive concurrency.
- **The tuning knobs teach the control-theory trade-off.** Presets are deliberately named for their failure modes: Aggressive oscillates, Sluggish reacts late and recovers slowly.

## Key design decisions and trade-offs
- **Tick-based model (20 ms) over discrete-event simulation.** Cheaper to build, deterministic, and its fidelity is sufficient for the lessons; the cost is 20 ms latency quantisation.
- **Backend = FIFO worker pool with variable service times; the thrashing penalty was removed.** The first version added an extra slowdown proportional to oversubscription so that throughput *collapsed* past capacity. It made the no-shedding lesson dramatic, but its shape was invented and hard to defend. A pool of `capacity` workers serving requests in arrival order is a model a reader can derive by hand (latency = queue wait + service time, throughput ≤ capacity ÷ service time) and every lesson still holds because the client deadline turns long waits into failures. With a *bounded* queue (any concurrency limit) throughput now plateaus at capacity ÷ service time instead of collapsing — so a capacity drop to 30% no longer made a static limit of 50 miss the SLA (50 ÷ 15 × 200 ms ≈ 670 ms), and the drop event deepened to 50 → 8 workers, where limit 50 waits ≥ 1.2 s and limit 25 sits at ~750 ms p99, to keep Lesson 3's dilemma visible. With an *unbounded* queue the collapse comes back on its own, and for a real reason: queue wait converges to the client timeout, so every worker is handed to a request whose client is about to give up — at 600 rps completions fall to zero by ~25 s. The meltdown Lesson 1 shows is emergent from FIFO plus deadlines, not something the model was told to do (and it is why real servers reach for LIFO or deadline-aware queues, listed under extensions). The Stable presets also tightened (AIMD threshold 2.0 → 1.3× baseline, Gradient tolerance 1.5 → 1.2×): with honest queueing, a loose latency threshold lets an adaptive limiter fill the queue to 2× capacity and double latency before it ever backs off; the tighter settings keep it near capacity for the first ~30 s (saw-tooth 50–65) and still drop it to ~10–15 during the event. The baseline drift this exposed under sustained load (the min-of-windows latency baseline never saw a queue-free window) is fixed by basing the baseline on processing time; see the adaptive-baseline bullet below.
- **Service time is bound when a request first gets a worker, not at admission.** With a queue, the two differ: the first version fixed the service time at admission, so a request queued during a downstream slowdown was still served 3× slower long after the slowdown ended (and one queued before it was served at full speed during it), roughly doubling Lesson 2's outage. Binding at service start means a request reflects the backend's speed at the moment it is actually worked on. Still deterministic — the per-request jitter is still keyed by request id.
- **Capacity is rounded to whole workers, and 0 means nothing is served.** An early guard clamped the pool to at least one worker to avoid a backend that silently serves nothing; that hid the one case where it matters — a capacity ×0 event is the honest model of an outage — and made the reported capacity disagree with the number actually serving. When capacity drops below the number already being served, the youngest of them pause and resume when a worker frees up (a CPU-stall model rather than a drain-then-shrink pool); simple, deterministic, and noted in the engine. The adaptive limiters get feedback only from completions, so during a capacity-0 outage they hold their limit until clients time out — no lesson wires that event today.
- **Clients abandon requests after `clientTimeoutMs` (10 s by default).** Without it the no-limit run's in-flight list grows forever under overload, so a long-running tab gets slower every tick and eventually runs out of memory. A client timeout bounds in-flight at offered rate × timeout (Little's law) inside the engine, deterministically, rather than pausing the UI after some wall-clock interval. It is also what a real meltdown looks like: latency pins at the timeout, goodput stays at zero. Abandoned requests are reported to the controller as completions at the timeout latency, which is the signal a real adaptive limiter gets from a timed-out call. A hard in-flight cap was rejected because dropping arrivals is itself an admission policy and would muddy "no limit".
- **Availability = good ÷ (good + failed), and pending requests are not failures.** The first version used `good ÷ offered` over the 1 s window, which silently counted every request still in flight as a failure — availability read 0% during the first second of any run and dipped whenever latency approached the window. Now only timed-out, rejected, and abandoned requests fail, plus in-flight requests already older than the SLA (they can no longer succeed, and without them a fully stalled backend would read 100% until its clients gave up).
- **p99 reports the age of the oldest in-flight request when nothing completes.** A fully stalled backend completes nothing in the sampling window, so a naive p99 would read 0 — the opposite of the truth. Found via a failing test.
- **The adaptive baseline is processing time, not latency.** The engine reports each completion's latency and, separately, the time it spent holding a worker; the limiters build their baseline from the latter (min of the last 30 window averages) and compare the window's mean latency against it. The excess is queue wait — the same "queue delay" signal Vegas and CoDel use. The first version used the min of window-average *latency*, and under sustained saturating load it never observed a queue-free window, so the baseline crept up with the queue and the limit drifted toward the maximum over minutes (AIMD Stable 60–95, Gradient Stable to 200); a periodic no-load probe would have been the alternative, but it costs throughput and a simulator can simply measure what a real server also knows. Processing time is unaffected by queue depth in this model, so the drift is gone; the bounded memory now only serves to let the baseline follow a genuine change in the backend's speed. Two consequences: a downstream slowdown looks like congestion until the baseline catches up (~15 s), so the limiter over-shrinks briefly — the same blind spot every latency-based limiter has; and a request the client abandoned has no known service time, so such windows are judged against the last baseline, and a limiter that has never seen a completed request holds its limit.
- **An adaptive limit only grows if at least half of it was in use during the window.** Healthy latency on its own is not evidence that a higher limit is safe — a lightly loaded backend reports healthy latency at any limit — so without this guard both AIMD and Gradient ratcheted to `maxLimit` in steady state and would have no headroom to shed with when load arrived. The guard uses the *mean* in-flight seen at admission attempts during the window (counting the request being admitted) and gates growth only; backoff under congestion still applies. Netflix's concurrency-limits gates on the peak instead; tried first here, it still crept — one Poisson burst that touched half the limit unlocked a growth step, growth is one-way, so a 60 rps backend ratcheted its limit ~10 per 10 minutes. Poisson arrivals see time averages, so the arrival-sampled mean is an unbiased utilisation estimate that a single burst cannot move. Under *saturating* load in-flight sits at the limit and growth is legitimately allowed; there it is the processing-time baseline (previous bullet) that stops the limit running away.
- **Gradient "Aggressive" preset headroom was cut from 20 to 12.** With `gradient` clamped at 0.5, `headroom` creates a floor of `2 × headroom` on the limit; at 20 the limiter could not shrink below 40 during a capacity drop to 15 and delivered zero goodput. A real pitfall of the algorithm, surfaced by a scratch trajectory run.
- **Custom canvas charts, no chart library.** 10 Hz updates across eight series, threshold lines, and clipped-but-labelled out-of-range values were simpler to own than to coerce out of a library. The categorical palette was checked with a CVD/contrast validator; the neutral reference lines were darkened after it flagged gray↔teal separation.
- **Identical A/B stretches are drawn as two-colour dashes, not one line.** Because both runs are deterministic and identical until demand exceeds capacity, the last-drawn (teal) line hid the red one entirely and the chart looked like only one run existed. Where a later series exactly matches an earlier one, the hidden colour is re-drawn as short dashes on top of that stretch; the lines separate on their own once the runs diverge. Rejected alternatives: a vertical offset (misrepresents the data) and a thinner top line (a halo that reads as a rendering artefact).
- **The flow animation is driven by the same metrics as the charts, not by individual simulated requests.** Dots spawn at `offered / 25` per second, are admitted with probability `admitted / offered`, and dwell in the backend for the mean latency (capped at 3 s, 150 dots per lane) — a stalled backend visibly fills up while its rejected neighbour streams through. Same-seed fairness is preserved because the animation only *reads* the runs. Mean latency needed the same "oldest in-flight age" fallback as p99: a stalled backend reported 0 ms and the dots flew straight through.
- **Layout: sidebar | simulation | notes.** The animation is the one bold element; charts are a flat grid with hairline gutters and stats are inline figures, so nothing competes with it. Lesson copy and knobs live in the right column so tuning reads as part of the lesson.
- **Scenario tests double as the tuning harness.** Each lesson's expected picture (e.g. "static 50 collapses during the drop, AIMD keeps goodput > 30 rps and recovers above 40") is a Vitest assertion, so the presets cannot silently drift.
- **Cut:** hover crosshair/tooltips on the charts (the live legend values cover the streaming use case), client retries, dark mode.

## How I'd extend it
- Client retries and retry budgets — the retry storm that turns a brown-out into an outage.
- Per-request cost classes and priority-aware shedding (drop cheap/low-priority work first).
- A dependency chain (two backends) to show how a concurrency limit at the caller protects the callee.
- Vegas- and CoDel-style limiters using queue delay rather than total latency as the signal.
- LIFO or deadline-aware queueing at the backend, so an overloaded FIFO stops spending workers on requests whose clients have already left.
- Shareable scenario URLs and record/replay.
