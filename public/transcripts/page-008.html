We don't — that guard is a mistake, and I'd remove it.

I wrote it defensively: if an event multiplier ever made capacity × multiplier round to 0, no request would progress, and I didn't want a config typo to produce a backend that silently serves nothing. But:

  1. Nothing can trigger it. The only capacity event is ×0.16 on 50 → 8 workers. It guards a case that doesn't exist.
  2. When it could trigger, it lies. A ×0 event is the honest model of "backend down". With the guard, the chart says capacity 0 while the engine quietly keeps one worker serving ~5 rps.
  3. Zero workers already works correctly. I patched the guard out temporarily and ran a ×0 event for 4 s: in-flight climbs, p99 tracks the oldest waiting request (1.2 s → 2.2 s → pinned at the client timeout), goodput 0, clients start abandoning at the timeout, and when capacity returns the backlog drains and availability recovers within a second. Nothing in the engine divides by capacity; the animation guards its own ratio.

Math.round stays — slots must be an integer for the i < slots comparison, and rounding keeps the reported capacity consistent with the served count.

So the line becomes const slots = Math.round(capacity); (and, per the review, the rounding moves into effective() so metrics report the same number the engine serves with), plus a test pinning the outage semantics. ## Motivation

The penalty made throughput *collapse* past capacity, which was dramatic but had a made-up shape that is hard to defend. A worker pool with a queue is a model a reader can derive by hand — latency = queue wait + service time, throughput ≤ capacity ÷ service time — and every lesson still holds because the client deadline turns long waits into failures.

Two consequences, both deliberate and recorded in `docs/RATIONALE.md`:

- **Capacity drop deepened from ×0.3 to 50 → 8 workers** (`CAPACITY_DROP`, Lesson 3/4 button and copy).
